## 해결하려던 문제

- **데이터:** 의료진이 검증한 이상행동 구간 라벨과 원본 영상의 시간이 일부 맞지 않았습니다. 그대로 자르면 실제와 다른 구간이 학습·평가 데이터에 섞입니다.
- **실시간 처리:** 감지 결과를 기존 병원 관제시스템으로 보내야 했지만, 네트워크 요청이 영상 추론을 멈추게 해서는 안 됐습니다. 프레임마다 알림이 나가는 것도 막아야 했습니다.
- **네트워크:** 병원 보안망에서는 전송이 실패했을 때 프로그램 문제인지 방화벽·보안 설정 문제인지 바로 구분하기 어려웠습니다.

## 주요 판단과 선택 이유

- **잘라 낸 결과는 원본 영상 타임스탬프와 직접 대조했습니다.** 코드가 오류 없이 끝났다고 데이터가 맞는 것은 아니었습니다.
- **라벨 수정은 의료진에게 맡겼습니다.** 라벨은 의료진이 검증한 기준이므로, 불일치를 보고하고 수정된 라벨 문서를 받아 같은 기준으로 다시 처리했습니다.
- **알림 여부는 일정 시간 동안의 판정 비율로 정했습니다.** 프레임마다 알림을 보내면 같은 상황에서 알림이 쏟아지고, 표본이 1~2개뿐일 때는 오판하기 쉽습니다.
- **전송은 영상 처리와 다른 스레드에서 했습니다.** 관제 서버가 느리거나 응답하지 않아도 추론 루프는 멈추지 않습니다.
- **요청과 응답을 모두 로그로 남겼습니다.** 병원 보안망에서는 실패 원인이 프로그램인지 방화벽·보안 설정인지 바로 알기 어려워, 판단 근거를 남겨 두려 했습니다.

### 2. 실시간 처리와 외부 통신 분리

최근 일정 시간의 판정을 모아 비율로 판단하고, 전송은 별도 스레드에서 처리합니다.

실제 코드에서 핵심만 추렸습니다.

```cpp
// 프레임마다 호출: 판정을 5초 창에 넣고, 창 밖으로 밀려난 판정은 버린다
void EventProcessor::OnNewFrame(int64_t labelId) {
  std::lock_guard<std::mutex> lock(mtx_);
  auto now = std::chrono::steady_clock::now();
  frameWindow_.push({ now, labelId });
  while (!frameWindow_.empty() && frameWindow_.front().first < now - kWindowDuration)
    frameWindow_.pop();
  CheckForAlert();
}

void EventProcessor::CheckForAlert() {
  auto now = std::chrono::steady_clock::now();
  if (now - lastAlertTime_ < kCooldownDuration) return;          // 60초 안에는 다시 보내지 않음
  auto span = frameWindow_.back().first - frameWindow_.front().first;
  if (span < kMinWindowDurationForAlert) return;                 // 2초 이상 쌓인 뒤에만 판단

  int alertFrameCount = 0;
  std::map<int64_t, int> eventCounts;
  for (auto q = frameWindow_; !q.empty(); q.pop()) {
    int64_t label = q.front().second;
    if (label != 3) { alertFrameCount++; eventCounts[label]++; } // 3 = background
  }
  if (alertFrameCount == 0) return;

  double proportion = static_cast<double>(alertFrameCount) / frameWindow_.size();
  if (proportion >= alertThreshold_) {                           // 50% 이상이면
    SendRestApiAlert(mostFrequent(eventCounts));                 // 가장 많이 나온 이상행동 하나만 전송
    lastAlertTime_ = now;
    clearWindow();
  }
}

void EventProcessor::SendRestApiAlert(int64_t eventId) {
  std::thread([=]() {                                       // 영상 처리 스레드를 막지 않음
    httplib::Client cli(host, port);
    cli.set_connection_timeout(5, 0);
    log("[API] Send alert. (Request: " + body + ")");
    auto res = cli.Post(path, body, "application/json");
    log(res && res->status == 200 ? "[API] Data sent successfully ..."
                                  : "[API-ERROR] ...");     // 실패 원인을 로그로 남김
  }).detach();
}
```

요청과 응답은 콘솔과 별도 API 로그 파일에 함께 기록해, 전송 실패 시 어느 단계에서 멈췄는지 확인할 수 있게 했습니다.

```text
[API] Send alert. (Request: {"Code":"<장비 코드>","Date":"2025-11-12","Info":"abnormal","Time":"21:41:48"})
[API] Data sent successfully (Response: "Y/전송완료")
[API] Send alert. (Request: {"Code":"<장비 코드>","Date":"2025-11-12","Info":"abnormal","Time":"21:42:48"})
[API] Data sent successfully (Response: "Y/전송완료")
```

같은 상황에서 알림이 60초 간격으로만 전송되는 것을 로그로 확인할 수 있습니다.

### 3. 현장에서 프로그램과 보안망 문제를 나눠 대응

현장 방문 전에 Linux `curl` 등으로 관제 서버 연결을 확인하는 방법을 준비했습니다. 병원에서는 애플리케이션 문제와 방화벽·보안 설정 문제를 분리한 뒤 전산팀과 함께 대응했습니다. [라이다 현장](/projects/lidar-ops/)에서 익힌 구간별 점검 방식을 그대로 썼습니다.

## 결과와 검증

- 재처리한 데이터로 모델 실험과 비교실험을 진행했습니다.
- 의료진과 배우가 참여한 현장 검증에서 이상행동 감지와 관제시스템 이벤트 전달을 확인했습니다.
- 전송 결과가 요청·응답 로그로 남아, 실패 시 프로그램·네트워크 중 어느 쪽 문제인지 확인할 근거가 생겼습니다.
